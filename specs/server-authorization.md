# Streamable HTTP authorization

🎯 Tachyon meets the Streamable HTTP rule "Servers **SHOULD** implement proper authentication for all connections". Every HTTP request is authenticated. State that outlives a request (2025-11-25 sessions, GET streams, replay; 2026-07-28 `subscriptions/listen`; tasks) is bound to the caller's principal. Without authorization configured, behaviour is unchanged. The application verifies tokens; Tachyon is never the authorization server.

## 2. Per-request authentication (both versions)

Authorization "**MUST** be included in every HTTP request from client to server" [A25/A26 §Token Requirements]. Every POST, and every 2025 GET and DELETE, is authenticated on its own. A session or an open stream never stands in for a token.

### Session binding

- A session records the owner key of the request that created it (`initialize`), or `null`. The key is fixed and persisted in `SessionSnapshot`.
- Every later POST, GET, DELETE or `Last-Event-ID` resume with that `Mcp-Session-Id` must resolve to an **equal** key; `null` equals only `null`. This matches Python; Go skips the check for anonymous sessions.
- Mismatch ⇒ `404 Unknown session`, the same response as an unknown id (`McpOperationHandler`), logged at warn with a truncated id. The session is not terminated. Go's `403` would reveal that the session exists.
- The `SessionIdGenerator` Javadoc ("must verify the principal") is replaced by a description of this binding.

## 5. Tasks

- **2025-11-25** [T25 §Task Isolation and Access Control]: "When an authorization context is provided, receivers **MUST** bind tasks to said context." "If context-binding is available, receivers **MUST** reject `tasks/get`, `tasks/result`, and `tasks/cancel` requests for tasks that do not belong to the same authorization context as the requestor. For `tasks/list` requests, receivers **MUST** ensure the returned task list includes only tasks associated with the requestor's authorization context." Without a context, tasks may be anonymous: "receivers **SHOULD** document this limitation clearly", and "receivers **MUST** generate cryptographically secure task IDs with enough entropy to prevent guessing". Tachyon documents the limitation (`docs/extensions/tasks.md`) but **mints no task id**: the tool or the task execution system does, so that **MUST** is the application's, which the docs say, and Tachyon cannot check it. Tachyon keeps declaring `tasks.list` (no breaking change).
- **2026-07-28** [T26 §Security Considerations]: "Servers **MUST** perform authentication and authorization checks on each task-related request to ensure that the client has permission to access a task." "A server **MAY** use task IDs as bearer tokens for a server's stored state. Servers **MUST** generate them with sufficient entropy that a third party cannot enumerate or guess them." Authentication is every request's (§2); authorization is the owner binding below plus the connector for what is unowned. The application mints the ids, as above.
- 🔴 **Deployment requirement.** The binding is process-local, so the 2025 **MUST** to "bind tasks to said context" holds on a clustered or restarted server only if the connector authorizes each call from `ctx.securityContext()`. Tachyon hands the connector the caller's own `DispatchContext` on every path: `tasks/get`, `cancel`, `update`, `list`, the legacy `result` wait and `cancel` wait, and the `subscriptions/listen` `taskIds` check. Proof: 2025 and 2026 `TaskOwnerBindingTest#theConnectorReceivesTheCallerOfEachRequestOnEveryTaskPath`. Stated in `docs/extensions/tasks.md` and `docs/running/authentication.md`.

| Entry point | Owner | Notify target | Progress token | Status |
|---|---|---|---|---|
| Task-augmented `tools/call` returns `ToolResult.task(...)` | the caller of that request (`Owner.of(context.securityContext())`), anonymous when unauthenticated | calling session (2025) | request's token | ✅ `TaskRuntime#publish(context, …)` → `TaskEngine#publishAs` |
| `InteractionContext#tasks().publish(s)` (new) | caller's | calling session (2025) | none | 🔴 Not built. A worker publishing before its tool returns must use `TachyonServer#tasks()`, which is unowned, so the tool's later owned create is refused (below). |
| `TachyonServer#tasks().publish(s)` | unowned (no caller): updates any task, claims none | none | none | ✅ `TaskEngine#publish` |

- ✅ **Owned task** (a named owner): reachable only by the same caller, from any session. Every other caller gets `Task not found`, the same answer as for an unknown id, before the connector runs. One gate covers all caller-facing paths: `TaskEngine#connector` returns the connector already guarded, so the real connector is unreachable from `tasks/get|cancel|result|update`, the `subscriptions/listen` `taskIds` authorizer and the legacy waits; `tasks/list` leaves foreign tasks out. Proof: `TaskOwnershipTest`, 2025 and 2026 `TaskOwnerBindingTest`.
- 🟡 **`tasks/list`.** T25 § Security Considerations: "For `tasks/list` requests, receivers **MUST** ensure the returned task list includes only tasks associated with the requestor's authorization context." Tachyon drops the tasks it knows are owned by someone else. A task nobody owns is not associated with any context, yet it is still passed through from the connector to every caller, so a connector that lists everything leaks unowned tasks to an authenticated caller. The same section says receivers that cannot identify requestors **SHOULD NOT** declare `tasks.list`; Tachyon keeps declaring it.
- ✅ **Unowned task** (anonymous creator, or server-published): left to the connector, which authorizes via `InteractionContext` (the recipe in `docs/extensions/tasks.md`, proof `TaskConnectorAccessTest`). Tachyon does not isolate it by session: that was #393, replaced by connector access, so "keeps #393's session isolation" is the connector's job, not the engine's.
- ✅ An owner never changes: a different owner is refused, and so is an anonymous caller on an owned task and a named caller on an unowned one. A refusal is decided before anything is touched (no snapshot update, no route attach, no push) and answers the generic `Internal error` on the tool path; it is logged with a truncated id. Same owner, newer revision ⇒ update. A publish without a caller never claims, so it updates an owned task.
- 🟡 **How long the binding lasts.** For the task's own `ttl`, even after the janitor evicts its snapshot; a task with no `ttl` is bound only while its snapshot is cached (terminal + `keepAlive`). In memory only: another node, or a restart, sees the task unowned and only the connector can still refuse. A shared binding store is not built.
- ✅ **A read never caches an unknown id.** `tasks/get`, `tasks/result`, `tasks/cancel` and the legacy waits update the cache through `TaskEngine#refresh`, which touches only a task the engine already holds and hands back an uncached connector snapshot with the engine defaults. A foreign or early read cannot leave an id unowned, so its creator's own `publishAs` still succeeds. Proof: `TaskEngineTest#refreshUpdatesACachedTaskAndNeverCachesAnUnknownOne`, `TaskOwnershipTest#noReadCachesATaskTheEngineDoesNotKnowSoItsCreatorCanStillOwnIt`, 2025 and 2026 `TaskOwnerBindingTest#aReadBeforeTheCreatorsToolReturnsDoesNotMakeTheTaskUnowned`. `TachyonServer#tasks().publish` is the only publish that creates an entry without a caller.
- Push (`notifications/tasks/status`, `notifications/progress`): ✅ 2025 ⇒ the route's session only, which is the creating caller's own session. ✅ 2026 ⇒ `subscriptions/listen` streams: an id owned by someone else is dropped when the stream opens and rechecked on every status pushed (L3). An id nobody owns stays the connector's call, made once at open. Never broadcast.

## API

As built (the names the code has; this section lists no planned shape):

- **Module split.** `tachyon-api` keeps what a handler author touches: `SecurityContext` (sealed: anonymous or authenticated, nothing between; extra claims go on the user's own `Principal` subtype), `InteractionContext#securityContext()`, `ToolDescriptor#requiredScopes` and `@McpTool(requiredScopes)`. Everything configured through `ServerBuilder#security` lives in `tachyon-core`, package `dev.tachyonmcp.core.server.security`: `AuthenticationProvider`, `AuthenticationRequest`, `AuthenticationException`, `AuthenticationChallenge`, `BearerTokenVerifier`, `VerifiedToken` (and `ScopeTokens`, `@InternalApi`). Their implementors already depend on core for `SecurityConfig`.

- `ServerBuilder#security(Consumer<SecurityConfig.Builder>)`. `SecurityConfig(Authentication authentication, Duration authenticationTimeout)`, where `SecurityConfig.Authentication` is sealed: `Disabled`, `Bearer` (its provider is derived from its `BearerConfig` and the server clock, and cannot be supplied) and `Custom(AuthenticationProvider)`. The builder's `bearerToken(Consumer<BearerConfig.Builder>)`, `authenticationProvider(provider)` and `authenticationTimeout(Duration)`: the last of the first two wins.
- `BearerConfig(resource, authorizationServers, scopesSupported, verifier)`: every rule (D1, D4, D5) is checked in its constructor, when `bearerToken(...)` is called.
- `AuthenticationProvider#authenticate(AuthenticationRequest)` returns a `SecurityContext` or throws `AuthenticationException`; it runs on the handler executor, **never on the event loop**, because introspection may block. `AuthenticationRequest` is a read-only view of the request head; `AuthenticationException` and `AuthenticationChallenge` build every rejection (K11).
- `BearerTokenVerifier#verify(String)` returns `VerifiedToken(Principal principal, Set<String> scopes, Instant expiresAt, Set<URI> audience)`: `expiresAt` is required, and an audience that may be empty is then never accepted (K4, K5).
- `InteractionContext#securityContext()` returns the caller of **this** request (K12): `principal()` (`null` when anonymous), `scopes()`, `expiresAt()`.
- `ToolDescriptor#requiredScopes()`, also `@McpTool(requiredScopes)` (S1).
- The owner of a session or a task is `Owner.of(SecurityContext)`: the principal's `getName()`, or anonymous. It is not configurable (❓ below).
- `SecurityConfig.Builder#accessPolicy(AccessPolicy)`: built, as `AccessPolicy` (V1), in place of the `AuthorizationPolicy` once sketched. Scope hierarchies have no `ScopeImplication` type: the verifier expands the scopes (S3).
- Not built, and not planned in this shape: `ServerBuilder#authorization(...)`, `TokenVerifier`, a Kotlin DSL and a Spring Boot property surface for `security`.

## Pipeline

`http` → `http-pipelining` → `http-keep-alive` → `dns-rebinding` (H1) → `mcp-endpoint` (lets the metadata paths through when bearer tokens are on) → `cors-mcp-param` → `cors` (preflight passes without a token) → ✅ **`protected-resource-metadata`** (D2, only with bearer tokens; consumes every request for its paths) → ✅ **`authentication`** (§2, on the request head; records the caller, K12) → `mcp-header-guard` → `protocol-version` → `accept-header` → `content-type` → `stateless-mcp` (stateless servers) → `http-aggregator` → `unsupported-protocol-version` → `interaction` → `idle` → `mcp-header-match` (L2) → the protocol's own request handlers → `mcp-phase-init` or `mcp-phase-operations`: ✅ **takes the caller** (K12), then session lookup + **binding** (§3) → decode → ✅ **scope check** (S1: `ToolsCallHandler`, after the tool is found, ahead of argument validation) → dispatch.

A 401/403 answers before any session lookup, SSE upgrade, replay or listen. A refused request is answered from its head: no body is read, `100 Continue` is never sent, and the connection closes. With authentication off, `authentication` and `protected-resource-metadata` are not installed, the handler that processes the request takes an anonymous caller, and the rest of the pipeline is unchanged (`HttpRequestPathBenchmark#authOff`).

## ❓ Open

- 2025: fan push out to every live session of the owner, instead of only the originating one?
- `notifications/*/list_changed` is broadcast to every session / listener: scope it per principal when per-principal lists differ?
- Cache `VerifiedToken` per token hash, bounded by `expiresAt`?
- Configurable owner key: today it is `Principal#getName()` (`Owner#of`). Multiple issuers need an owner-key function on `security(...)`, for example `(client_id, iss, sub)`. Sessions and tasks both read it, so it must be one function.
- A Kotlin DSL `security { }` and a Spring Boot property surface for authentication; a bridge from Spring Security's `Authentication` (already a `Principal`). Only the Java `ServerBuilder#security` exists.
- Scopes (S1): `resources/read`, `prompts/get` and other methods have no `requiredScopes`; `tools/list` is not filtered by a caller's scopes (S4: scopes are a step-up; the access policy hides, V1); a tool's scopes are not checked against `BearerConfig#scopesSupported`; the Kotlin flat `tool(...)` overloads do not take `requiredScopes`; scope hierarchies (S3) are the application's, expressed by expanding the scopes it reports.
- Discovery (D2): a custom provider publishes nothing and has no Protected Resource Metadata; a gateway that rewrites the path prefix must forward the well-known path unchanged, because the handler matches the public resource path.
- Re-run `HttpRequestPathBenchmark`, `ToolCallDispatchBenchmark` on a quiet machine before release (every JMH A/B on this branch ran under load; see `.llm-wiki/findings.md`).

✅ Acceptance (E2E, port 0, both protocol versions unless marked):

- **Unconfigured:** every existing E2E passes unchanged; `tasks.list` is still declared.
- ✅ **Discovery:** request without a token ⇒ `401` + `WWW-Authenticate: Bearer resource_metadata="…", scope="…"`. Both well-known URIs serve PRM without a token. With `resource = https://api.example.com/mcp` and a plain-HTTP request whose `Host` / `X-Forwarded-Host` is spoofed, `resource` and `resource_metadata` still name `https://api.example.com` (`DiscoveryTest`, 2025 and 2026).
- **Tokens:** expired, wrong audience, or bad signature ⇒ `401 invalid_token`. `?access_token=` ⇒ `400`. No log line at INFO or DEBUG contains the token: the DEBUG wire log carries sizes only (`WireLogTest`). The TRACE wire log carries the bytes, so it stays off in production. Handlers cannot read the raw token.
- **Head authentication (K10):** no token + `Expect: 100-continue` + a body declared above `maxContentLength` ⇒ `401`, no `100 Continue`, no `413`, connection closed. An invalid protocol version without a token ⇒ `401`, not a version error; with a token ⇒ `400` as before. A preflight without a token ⇒ the normal CORS answer. A refusal carries the CORS headers. A verifier that never answers ⇒ `503` + `Retry-After`, no challenge, within the configured timeout. A valid token with a body of 512 KB, with and without `Expect`, over a slow verifier ⇒ success with the body intact (`HeadAuthenticationTest`).
- ✅ **Scopes (`tools/call`):** missing scope ⇒ `403 insufficient_scope` with every required scope in one challenge, before any SSE bytes. The policy sees the body's tool name, not a forged `Mcp-Name` (`RequiredScopesTest`, 2025 and 2026).
- **2025 sessions:** session created by A, a POST/GET/DELETE from B or anonymous ⇒ `404`; A unaffected. An anonymous session rejects an authenticated caller. `Last-Event-ID` from B ⇒ `404`, nothing replayed. A restored session keeps its owner key.
- **2026 listen:** B's listen never receives A's task status. ✅ The listen stream closes at token `expiresAt` and a fresh token listens again (`TokenLifetimeTest`).
- **Tasks:** same principal, two sessions (2025) ⇒ `tasks/get` succeeds from both. A different principal ⇒ `Task not found`, connector not called. An anonymous task on a stateful 2025 server ⇒ only the creating session reaches it (#393 unchanged). `ctx.tasks().publish` from a plain tool ⇒ `server.tasks().get(id)` is non-null. A job publishing before its task tool returns ⇒ the call succeeds with the same owner. Anonymous publish, then an owned `create` ⇒ refused.
