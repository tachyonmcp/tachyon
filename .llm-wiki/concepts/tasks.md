# ⏳ Tasks

Verdict: Tachyon does **not** run tasks. External system owns execution via `TaskConnector` functions; Tachyon keeps a revision-ordered projection cache (`TaskSnapshot`), maps MCP task methods to connector calls, and pushes status/progress notifications. All `@ExperimentalApi`.

## ⚙️ Config

`withExtension(TasksExtension.class, t -> t.connector(c))` ⇒ registered = enabled; no capability switch, no auto-registration. No connector ⇒ ISE `TasksExtension.Builder#build`; `TaskEngineSettings` validates pageSize/pollInterval > 0, keepAlive default **5 min** (`TaskEngineSettings#DEFAULT_KEEP_ALIVE`). Kotlin: `tasks(connector) { }` on `TachyonServerBuilder`. Runtime access: [TasksExtension#tasks(TachyonServer)](../../extensions/tachyon-extensions-tasks/src/main/java/dev/tachyonmcp/extensions/tasks/TasksExtension.java) (callbacks) and `TasksExtension#tasks(InteractionContext)` (tool handlers, via `InteractionContext#extension`). Both ⇒ ISE "TasksExtension is not registered…" when absent; thrown in a tool handler ⇒ `-32603`. Instance `TasksExtension#tasks()` ⇒ ISE before build. Façade server-scoped: background work keeps it, never `ctx`. Kotlin: `TachyonServer.tasks` + `ToolScope#tasks`. Install phase `TasksExtension#install` (before any extension bootstraps): engine ⇒ `McpTaskBinding` listener ⇒ `ServerEngine#installTaskRuntime`. So task-capable tools registered in another extension's `bootstrap` pass the `DefaultToolRegistry#register` check even when that extension comes first. Bootstrap `TasksExtension#attach`: `TaskMethodHandlers#register` ⇒ janitor start.

Registration check: registering a `REQUIRED` or `OPTIONAL` tool w/o tasks extension (`TaskRuntime#executionConfigured`) ⇒ `IllegalStateException("Tool '<name>' declares task support, which requires TasksExtension")`, at build (bootstrap registrations ⇒ build fails, server closed) or after it `DefaultToolRegistry#register`. Extensions bootstrap before registrations, so the runtime is already installed.

## 🔁 Task-producing tool call

`ToolMethodHandlers` `validateTaskRequest` `ToolsCallHandler#validateTaskRequest` + `mapResult` `ToolsCallHandler#mapResult`:

| Protocol | Rule |
|---|---|
| 2025-11-25 (legacy augmentation) | client sends task-augmented call; `FORBIDDEN`/absent + augmented ⇒ -32601; `REQUIRED` + plain ⇒ -32601 (§ Tool-Level Negotiation) |
| 2026-07-28 | no augmentation flag; `REQUIRED` ⇒ tasks extension must be declared (else -32021) |

Tool returns `ToolResult.task(snapshot)` ⇒ checks (not FORBIDDEN, legacy must be augmented, extension declared on modern) ⇒ `taskRuntime().publish(context, snapshot, progressToken)` ⇒ `McpTaskBinding#publish` ⇒ `TaskEngine#publishAs(context, snapshot, McpTaskRoute.of(context.sessionId(), token))` (explicit: async tools map off the dispatch thread, and the dispatch context is the request's own fixed copy) ⇒ `createTaskResult`, observation outcome `TaskHandoff`. The caller owns the task; an owner conflict ⇒ ISE ⇒ generic `Internal error`, no `TaskHandoff`. Non-task result for REQUIRED/augmented ⇒ internal error.

## 🗂️ Registry semantics

Verdict: cache + push **routing**, plus an **owner key on the snapshot**. A `TaskRoute` (session + progress token) is a delivery address, never an owner. The owner is `TaskSnapshot#ownerKey` (`@Nullable`, server-side only, never mapped to the wire), three states: a caller's key = **owned**, that caller only; `TaskSnapshot#PUBLIC_OWNER_KEY` (`"<public>"`, defined once as `SecurityContext#PUBLIC_OWNER_KEY`; `AuthenticatedSecurityContext` refuses it as a caller's key, and `TaskSnapshot#check` refuses a blank key, so a lost owner never reads as public) = **public**, every caller; `null` = **unowned**, nobody on a server with authentication. The connector stores it with the task and returns it, so a restart, another node, or an evicted entry still knows it; on its own node the engine also remembers an evicted task's owner until `createdAt + ttl` (`TaskEngine#retain`). Every caller-facing path goes through the **guarded connector** (`TaskEngine#connector`), which answers anyone else `TaskNotFoundException` exactly as for an unknown id, and leaves foreign tasks out of `list`.

- **Stamped on handoff.** `TaskEngine#publishAs(ctx, snapshot, route)` stamps `TaskSnapshot#ownerKeyOf(ctx.securityContext())` on the snapshot (`TaskEntry#withOwner`): the caller's key, or the public key for an anonymous caller. A snapshot already carrying a different key, a cached entry whose owner is not that key (`TaskEngine#mayPublishAs`: someone else's, or nobody's; one exception, an anonymous caller where `TaskEngineSettings#shareUnownedTasks` holds, and the entry becomes public), or an evicted id whose remembered owner is not the caller (`TaskEngine#place` with `claim`) ⇒ refused (`IllegalStateException`) before anything is touched, so a refused claimant's route never attaches (`TaskEntry#publish` runs before `TaskEntry#route`). `TaskEngine#publish(snapshot)` (the `Tasks` façade) has no caller: a snapshot without `ownerKey` keeps the known owner, one naming an owner gives it to a task nobody owns yet, one naming another owner ⇒ ISE. `TaskEngine#refresh(snapshot)` caches nothing for an unknown id, lets an unowned cached entry take the owner the connector names, and does not cache a read naming a different owner. `TaskEntry#publish` is the one arbiter: an unowned entry adopts the candidate's owner whatever its revision, a conflicting owner changes nothing. An owner never changes.
- **Two sources, both must admit.** `TaskEngine#admits(caller, known, stored)`: the owner the engine knows (`TaskEngine#knownOwner`: the cached entry's, else the one remembered since eviction) and the stored snapshot's `ownerKey` must each be null, public or the caller's key (`TaskEngine#reaches`). Both null (unowned) ⇒ admitted only with `TaskEngineSettings#shareUnownedTasks`, for every caller: `TasksExtension#install` sets it from `TasksExtension.Builder#shareUnownedTasks` (default `false`; Kotlin `TasksScope#shareUnownedTasks`) or when the server has no authentication (`SecurityConfig.Authentication.Disabled`). Proof: `TaskOwnershipTest#aPublicTaskReachesEveryCallerAndStaysPublic`, `#aTaskNobodyOwnsIsHiddenFromEveryCallerUnlessTheServerSharesIt`, e2e 2025 `TaskOwnerBindingTest#anAnonymousCallersTaskIsPublicAndATaskNobodyOwnsReachesNoCaller`.
- **One gate.** `TaskEngine#guard`: `get` checks the known owner before the real connector runs, then the returned snapshot; `cancel`/`update`/`awaitResult` go through `TaskEngine#requireReachable`, which decides from the known owner and reads `get` first only when the engine knows none (one extra connector call); `awaitResult` also checks the snapshot its hook returns, since the task can gain an owner while the hook blocks (`TaskOwnershipTest#aTaskOwnedByTheTimeTheAwaitHookReturnsIsHandedToItsOwnerOnly`); `list` filters by `admits`. Evicting an entry before its ttl, the janitor keeps its named owner in `TaskEngine#retain` until `createdAt + ttl`; `TaskEngine#remove` forgets it. No ttl ⇒ nothing outlives the entry. `TaskMethodHandlers` has no ownership code.
- ⚠️ Limits: the remembered owner is one node's memory, so the connector must persist and return `ownerKey`, or an owned task reads as unowned after a restart, on another node, past its ttl, or once evicted without a ttl (then hidden from every caller on a server with authentication, open to all with `shareUnownedTasks`); `list` is filtered after the connector's page, so a page can come back short with a valid cursor. `InteractionContext#tasks()` (spec "new") is not built, so a worker that publishes before its tool returns publishes unowned unless it sets the caller's `ownerKey` on the snapshot; the tool's later create of an unowned entry is refused (the anonymous exception above aside).

- effective pollInterval = snapshot's or config default, then the binding's normalizer `TaskEngine#withDefaults`. Every cached or returned snapshot passes here. The MCP binding's normalizer serializes a `Completed` result's structured payload with the server serde (`ServerEngine#payloadSerializer`) so `tasks/get`, `tasks/result` and status notifications encode it like `tools/call` `TasksExtension#serializeResult`; the engine itself imports no serde (`EngineBoundaryTest`).
- `publish(snapshot)`: upsert through `TaskEngine#place` (`computeIfAbsent`, unrouted). Uncached ⇒ cached unrouted; cached ⇒ `TaskEntry#publish` accepts only **higher revision**; changed ⇒ `TaskEntry#notifyIfNewer` `TaskEngine#publish`. No cache-change callback: publish/remove/eviction push nothing beyond per-task status.
- `publishAs(ctx, snapshot, route)` (tool path): `TaskEngine#place`; existing entry takes `route` only if unrouted (`TaskEntry#route(TaskRoute)`: set once, never re-routed, colliding call succeeds) `TaskEngine#publishAs`. Route attach itself pushes nothing: the tool result carries that revision; revisions sent before attach are not re-sent.
- `tasks/get|cancel|result` `TaskEngine#refresh` the connector's snapshot ⇒ a cached task is updated, an unknown id is never cached; a read never routes. `tasks/list` never caches.
- Route source: only the task-augmented `tools/call`, never a thread, facade or read. No `InteractionContext#tasks()`.
- Task ids come from the tool or engine, never Tachyon; unguessability is their job (spec MUST without context binding).
- `reportProgress(taskId, …)` fires `TaskEvents#onProgress`; the MCP binding drops it without an `McpTaskRoute` progressToken `McpTaskBinding#onProgress`.
- Threading: `TaskEntry` lock guards publish + route + notify. `TaskEntry#notifyIfNewer` gates on `notifiedRevision`, so a publisher that lost the race never sends a stale status. Sends run under the lock, so session status uses `offerEvent` (slow client ⇒ its stream closes, publishers never park) `DefaultTachyonServer#notifyTaskStatus`.
- Janitor every 30s removes entries past `createdAt + ttl` (any status, any route) or terminal and cached longer than keepAlive `TaskEntry#isExpired`, `TaskEngine#runJanitorSweep`. Eviction drops the route: later status reaches listeners only.

Notification routing [McpTaskBinding#onStatus](../../extensions/tachyon-extensions-tasks/src/main/java/dev/tachyonmcp/extensions/tasks/McpTaskBinding.java) ⇒ [DefaultTachyonServer#notifyTaskStatus](../../tachyon-core/src/main/java/dev/tachyonmcp/core/server/DefaultTachyonServer.java): routed ⇒ that session gets `notifications/tasks/status` (gone ⇒ nothing, no fallback). The binding also calls [SubscriptionRegistry#publish](../../tachyon-core/src/main/java/dev/tachyonmcp/core/server/features/subscriptions/SubscriptionRegistry.java) for `notifications/tasks` on streams naming the task id. The tasks extension owns the `taskIds` topic: [McpTaskBinding#taskIdsTopic](../../extensions/tachyon-extensions-tasks/src/main/java/dev/tachyonmcp/extensions/tasks/McpTaskBinding.java) requires client declaration and narrows ids via [TaskEngine#readableTaskIds](../../extensions/tachyon-extensions-tasks/src/main/java/dev/tachyonmcp/extensions/tasks/engine/TaskEngine.java) (connector `get` per id with listener context, fail closed). The filter value is a `TaskListen(listener Owner, taskIds)`, the listener taken from the listen request's `SecurityContext`. The ack echoes only honored ids. No tasks extension ⇒ `taskIds` is unknown and ignored. The connector is asked once per stream; every pushed status is rechecked with `TaskEngine#admits(listener, snapshot)` against the snapshot's `ownerKey` (public admitted for every listener: e2e 2026 `TaskOwnerBindingTest#aSignedInCallersStreamFollowsAnAnonymousCallersTaskButNotOneNobodyOwns`), so a stream that named an id before the task existed stops following it once someone else owns it. A snapshot naming no owner goes to every stream admitted at open: the owner keeps following a task republished without `ownerKey` (e2e 2026 `TaskOwnerBindingTest#theOwnersStreamStillFollowsATaskTheApplicationPublishesWithoutAnOwner`). Eviction/route loss changes nothing for listeners. Never broadcast. [McpResponseMapper#subscriptionNotificationParams](../../tachyon-core/src/main/java/dev/tachyonmcp/core/protocol/mcp/v2026_07_28/codecs/McpResponseMapper.java) merges the stream's `_meta.io.modelcontextprotocol/subscriptionId` over snapshot metadata (server key wins); session `notifications/tasks/status` stays on `taskStatusNotificationParams` without it. Session payloads use the session protocol's `ProtocolResponseMapper#encode`. No `tasks/list_changed`: neither MCP 2025-11-25 (`tasks` cap = `list`/`cancel`/`requests`) nor the 2026-07-28 tasks extension (no `tasks/list`) defines it; `TaskPushRoutingTest#taskSetChangesReachNoSessionButTheOwner`.

History: beta.30 inferred the route from the `OutboundSseStreamMessageRouter` ThreadLocal and broadcast unrouted status to every session; beta.31 (#393) made the session an owner with `visibleTo` gates. Both replaced by explicit route + connector access.

### ❓ Why the route is not in `TaskSnapshot`

Route = server-local delivery state in `TaskEntry` (set once by `TaskEngine#publishAs`); `TaskSnapshot` = the external system's view, authored by connector/engine.
- `Mcp-Session-Id` is session state: snapshots flow to connectors, external stores and logs.
- Connector-authored `publish` would have to carry the route ⇒ either it can re-route (breaks set-once) or the field is ignored (misleading).
- Snapshots map straight to wire types (`McpTaskMapper`): one missed mapper leaks a session id.
- 2026-07-28 has no sessions; the spec binds tasks to the authorization context, not a transport session. The owner is `TaskSnapshot#ownerKey`, an owner key from the authorization context, never the route.

Legacy sticky `cancelled` (2025-11-25 § Task Cancellation 2–3: status ≠ execution) also belongs to the connector: `get` should report `cancelled` once `cancel` is accepted; Tachyon never pins it in the cache (not durable, overwritten by higher revisions) and only waits `TaskEngine#cancelAndAwait`.

Durable ownership rides the snapshot: the connector stores `TaskSnapshot#ownerKey` and returns it on every `get`/`list`, so restart and multi-node hold (e2e `aRestartedServerStillHidesTheTaskFromAnotherCaller`, both versions). Every path still hands the connector the request's own context (e2e `theConnectorReceivesTheCallerOfEachRequestOnEveryTaskPath`), so a connector may authorize further.

Gates thrown from `decode` as `RequestMappingException` `RequestMappingException`.

Wait release, never task cancel: disconnect on a live session keeps waiting (resumable via `Last-Event-ID`); session end or, without a session, connection close completes `responseUndeliverable` and the poll loop returns; `notifications/cancelled` interrupts. ## 🔌 Temporal integration

`TemporalTaskExecutionEngine` → `connector()`; MCP task id = Workflow id; routes (`TemporalTaskRoute`) define workflow type, start args, status query, snapshot mapper, input update `TemporalTaskExecutionEngine`. `TemporalTaskExecutionEngine#start` writes the caller's `TaskSnapshot#ownerKeyOf` to the Workflow memo `TemporalTaskExecutionEngine#OWNER_MEMO`, and `TemporalTaskExecutionEngine#attach` (one `describe` for owner and route) answers any other caller of `refresh`/`cancel`/`submitInput` with `TaskNotFoundException`. Key, not principal name: two tenants' same-named callers are two owners (`TemporalTaskExecutionEngineTest#aWorkflowBelongsToTheCallerThatStartedItOnEveryEngine`). Snapshots from `start`/`refresh` carry the memo owner as `ownerKey`. Anonymous start ⇒ memo `TaskSnapshot#PUBLIC_OWNER_KEY` ⇒ public, every caller reaches it (`TemporalTaskExecutionEngineTest#aWorkflowStartedAnonymouslyIsOpenToEveryCaller`). An empty memo is nobody's key ⇒ reaches no caller, `unownedAccess` not asked (`TemporalTaskExecutionEngineTest#aWorkflowWithoutOwnerMemoIsReachedOnlyByCallersUnownedAccessAdmits`). No memo at all (pre-upgrade or started outside the engine) ⇒ **not** open: `TemporalTaskExecutionEngine.Builder#unownedAccess` (`BiPredicate<InteractionContext, taskId>`) is asked on every call, default refuses all ⇒ `TaskNotFoundException`; an admitted caller does not become the owner: the snapshot carries no `ownerKey`, so on a server with authentication every caller also needs `shareUnownedTasks`. Apps keep their old per-request check there until those Workflows finish. The stub `attach` returns is pinned to the described run (`WorkflowTargetOptions` with the run id, not the bare Workflow id), so a run replaced under the same id is never reached through its predecessor's owner; the SDK deprecates the stub built from a bare `WorkflowExecution` because it does not account for the run id (it drops it on `cancel`). A `cancel` on a closed run is `WorkflowNotFoundException` per its Javadoc, so the same `TaskNotFoundException`; queries on a closed run are served within retention. Test double: `tachyon-testkit/src/main/java/dev/tachyonmcp/testkit/TestTaskConnector.java`. See [[integrations]].
