# 🔎 Findings

Spotted while reading code. Runtime verification noted per finding. Fixed in code ⇒ 🗑️ remove row.

- 🐛 ts2java nested arrays: `Array<Array<string>>` / `string[][]` model is `List<List<String>>` but the codec decodes elements via a bogus `Lis` codec. No current schema uses it. Probe-verified. [Generator#add_codec](../tachyon-core/ts2java.py)
- 🪶 Extension close hook is unused: `Extension#onConnectionClose` has no server call site. Cleanup currently relies on `ServerExtension#shutdown` during terminal close. Static source search. [Extension#onConnectionClose](../tachyon-api/src/main/java/dev/tachyonmcp/api/runtime/Extension.java), [DefaultTachyonServer#close](../tachyon-core/src/main/java/dev/tachyonmcp/core/server/DefaultTachyonServer.java).
- ⚠️ `UnsupportedProtocolVersionHandler` encodes the rejection with `ProtocolVersionHandler#LATEST_PROTOCOL` (not `Protocols#baseline`) + HTTP 400, even for legacy-looking clients. Intentional per SEP-2575? `UnsupportedProtocolVersionHandler#channelRead`
- ⚠️ POST-SSE budget per stream only; no global cap or connection limit. `PostSseStream#reserve`
- ⚠️ Perf: notifications round-trip bytes → `String` → bytes. `DefaultTachyonServer#sendSerializedNotification` builds `notificationJson` as a `String`; `SseSerializer#measure` then counts its UTF-8 size (~0.7 ns/char, charAt loop, not vectorized) and `SseSerializer#encode` transcodes it back. Carry `byte[]` end to end (like the final response, `PostSseStream#writeEvent(long, byte[], Runnable)`): length is free, encode is a copy. Touches `SseEvent`, `JsonRpcCodec`, event log (stores `String`).
- ⚠️ Several producers on one POST-SSE stream: a parked producer can be overtaken ⇒ wire ids out of order ⇒ `Last-Event-ID` resume may skip one. Pre-existing race, wider with parking. `PostSseStream#awaitCapacity`
- ⚠️ Platform `ServerBuilder#threadFactory`: parked producer holds an OS thread until `writerIdleTimeout`. `DefaultServerBuilder#build`
- ⚠️ For a task nobody owns Tachyon has no access control of its own: `tasks/*` go to the connector, and `subscriptions/listen` task ids pass the connector's `get` once when the stream opens ([McpTaskBinding#taskIdsTopic](../extensions/tachyon-extensions-tasks/src/main/java/dev/tachyonmcp/extensions/tasks/McpTaskBinding.java), [TaskEngine#readableTaskIds](../extensions/tachyon-extensions-tasks/src/main/java/dev/tachyonmcp/extensions/tasks/engine/TaskEngine.java)), not per event (an id owned by someone else is rechecked per event against the owner, in memory): a permission the connector revokes later keeps flowing until the stream closes. Safe only with unguessable task ids (MCP tasks spec MUST without context binding); Tachyon cannot check ids it doesn't mint.
- ⚠️ Listen: one sequential connector `get` per task id, bounded only by `maxContentLength`. `TaskEngine#readableTaskIds`
- 🪶 A publish racing janitor eviction can land on the evicted entry: `putIfAbsent` returned it, then `TaskEntry#evictIfExpired` removed it before `TaskEntry#publish`. The status is still sent, but the newer revision is not cached. Benign: the cache is a projection and the next `tasks/get` re-caches the connector's snapshot. Pre-existing (the old `entries.get` path had the same window). `TaskEngine#publish`
- ⚠️ `working` task with `ttl = null` never evicted. `TaskEntry#isExpired`
- ⚠️ SEP-2640 `"resources": "dynamic"` unsupported. The schema carries `SkillResource[] | "dynamic"`, but `skills-2026-07-28_config.json` maps `Skill.resources` to `List<SkillResource>`, and `SkillsRegistry.Skill` has no dynamic flag, so a generated-content skill can't be served. Fix needs both: a wire model for the union (generator support or a `JsonNode` mapping) and a registry API for dynamic skills. `SkillsExtension#skillEntry`
- 🪶 Blocking custom `SessionEventStore#append` serializes a task's publishers (per-task lock). `TaskEntry#notifyIfNewer`
- 🪶 A2A placement undecided: the tasks `engine` package is protocol-neutral so it can become `tachyon-tasks` (MCP binding + future A2A binding on one engine). If A2A ships inside `tachyon-core`, the engine must move into core instead (core cannot depend on an extension). Decide before the split; engine ownership when both bindings are present is open. `EngineBoundaryTest`
- 🪶 Dead code: `DefaultTachyonServer#drainEvents` has no caller; `Session#cursor` only feeds it. Delete or wire up. `DefaultTachyonServer#drainEvents`
- 🪶 Task codecs still live in core (`McpTaskMapper` v2025/v2026, task methods on `ProtocolRequestMapper`/`ProtocolResponseMapper`, `capabilities.tasks` in `ServerInfoMapper`); the generated `…extensions.tasks.protocol.v2026_07_28` models are unused. `McpTaskMapper`
- ⚠️ Kotlin DSL defaults to the Jackson serde, which cannot decode Kotlin data classes: `arguments.decode<T>()` and `typedTool` fail with `-32602 … could not be decoded` until `json { serde = KxSerializationSerde.Default }` is set. Verified at runtime (doc-examples `ToolExamplesTest`). `TachyonServerBuilder#json`
- 🪶 `ServerBuilder#pipelineCustomizer` keeps a single customizer: a second call replaces the first instead of composing. Verified at runtime (doc-examples `RegistrationExamplesTest`). `DefaultServerBuilder#pipelineCustomizer`
- 🪶 `McpOperationHandler` logs `MCP request: {method} {uri}` at DEBUG with the full `req.uri()`, query included. The bearer provider refuses `?access_token=` first, but a custom `AuthenticationProvider` that accepts a credential in the query would see it logged. Log the path only, as `AuthenticationHandler#path` does. Static read, not run. `McpOperationHandler#handleRequest`

## 🪶 Polish

- 🪶 Coroutine API gap: task connector hooks and raw extension handlers expose synchronous Java SAMs; Kotlin's suspend adaptation currently covers tools/resources/prompts/completions. Blocking connectors remain supported; suspend clients need their own bridge. Add adapters only for an actual coroutine integration. Static review only. [TaskGetFn#apply](../tachyon-api/src/main/java/dev/tachyonmcp/api/server/features/tasks/TaskGetFn.java), [ExtensionMethodHandler#handle](../tachyon-api/src/main/java/dev/tachyonmcp/api/server/extensions/ExtensionMethodHandler.java), [toolFn](../tachyon-kotlin/src/main/kotlin/dev/tachyonmcp/kotlin/server/features/tools/ToolHandlerFactory.kt).
- 🪶 [TachyonServer#registerTool](../tachyon-kotlin/src/main/kotlin/dev/tachyonmcp/kotlin/server/TachyonServer.kt): `configure` runs once, but overridable interface members cannot declare contracts. Fix requires API reshaping.
- 🪶 `SessionConfig` is a sum modelled as a product: `boolean enabled` × 5 `@Nullable` options, guarded in the compact ctor **and** `Builder#build`. Stateless is a *server* property — no session config ⇒ no sessions. shape: drop `enabled`, make every component non-null, `@Nullable SessionConfig ServerConfig#session()` with `stateless()` derived from `== null`, delete `SessionConfig#sessionStoreOrDefault`/`#sessionEventStoreOrDefault` and `Builder#enabled`/`#enabled(boolean)`. Then the impossible state is unrepresentable in the value, not just the builder.

## ❓ Open questions

- **Q:** Multi-node `SessionEventStore` replay? - **A:** No
- 2026-07-28 + stateful server: dispatcher bypasses sessions via `supportsSessions=false`; GET stream not matched for 2026 → only `subscriptions/listen`. Confirm intended.
- ⚠️ `MISSING_REQUIRED_CLIENT_CAPABILITY` maps to -32003 on 2025-11-25 (`McpResponseMapper`), -32021 only on 2026-07-28. SEP-2133 / Python SDK use -32021. Decide whether the 2025 wire should switch.
- ⚠️ Generated skills `Skill.resources` is `List<SkillResource>` (config override): schema's `SkillResource[] | "dynamic"` has no ts2java mapping. Fine while registries only publish scanned files; dynamic skills need a union type. `extensions/tachyon-extensions-skills/protocol/skills-2026-07-28_config.json`
- ⚠️ Legacy waits poll `get` per `pollInterval` each: N waiters ⇒ N/interval connector calls. `TaskEngine#pollUntilTerminal`
- ⚠️ `responseUndeliverable` node-local: `DELETE` on another node leaves waiter polling until local janitor evicts. `Session.InFlightRequest#sessionClosed`
- ⚠️ Owner binding guards later requests, not creation: a custom `SessionIdGenerator` returning a predictable id (tenant-derived) lets any caller's `initialize` replace that id's live session; `SessionManager#createSession` closes the previous generation. Static read, not run. `SessionManager#createSession`
- ⚠️ 2026-07-28 Streamable HTTP § Earlier Streamable HTTP Revisions: a server without protocol sessions **SHOULD** answer GET and DELETE with `405` and **ignore** `Mcp-Session-Id` and `Last-Event-ID`. A stateless Tachyon server answers `DELETE` with 405, but a `GET` without session headers opens an SSE stream (`SseManager#openStatelessStream`), and any request carrying `Mcp-Session-Id` or `Last-Event-ID` gets `404` (`StatelessValidatorHandler#channelRead`) instead of being ignored. Verified by running the 2026 DELETE and header cases; GET by static read. The spec's SHOULD is for "a server that supports **only this revision**"; a stateless Tachyon also serves 2025-11-25, where a `GET` stream and `404` on an unknown session id are right, so ignoring and `405` would key off the `MCP-Protocol-Version` the request names. `../specs/features/auth` L1 is 🟡.
- 🪶 Restore the `RedisSessionStore` example after Tachyon 1.1 is published. CI job `examples (doc-examples)` (`.github/workflows/examples.yml`, `./mvnw clean verify` in `examples/doc-examples`) builds against the **released** `tachyon.version` 1.0.1, whose `SessionStore#create(key, expiresAt)` is not the 1.1 `create(key, @Nullable ownerKey, expiresAt)` that `RedisSessionStore` implemented, so the job could not compile. Parked, CI untouched: `git mv` to `examples/doc-examples/parked/RedisSessionStore.java` with a README, outside the source root; `McpConfiguration` now takes the `SessionStore` interface (still the synced `springboot_customizer` snippet), `SpringBootReferenceTest` uses `InMemorySessionStore` and `store.find(sessionId)`. Proof: `cd examples/doc-examples && ../../mvnw -q -o compile` green, `SpringBootReferenceTest` 2/2, `make docs-check` green. When 1.1 ships: bump `tachyon.version`, move the file back, restore the counting assertion. A new doc-example that uses `SecurityContext` or the auth SPI hits the same wall until then, which is why `docs/running/authentication.md` shows those blocks as plain fences. `examples/doc-examples/parked/`
- 🪶 Per-item `AccessPolicy` calls: a list asks the policy once per registered feature, on the request thread, and a `subscriptions/listen` or `resources/subscribe` URI is matched against every template (`DefaultResourceRegistry#isHidden`). Fine for hundreds of features; a server with very many templates or an expensive policy would want a per-request cache. `Visibility#of`, `DefaultResourceRegistry#isHidden`
- 🪶 `resources/unsubscribe` checks no visibility: it only removes what the session itself recorded, and a hidden URI was never recorded (`ResourceMethodHandlers` subscribe handler). `ResourceMethodHandlers`
- ⚠️ RFC 9728 § 3.3: "The resource value returned MUST be identical to the protected resource's resource identifier value into which the well-known URI path suffix was inserted". For a resource with a path, the root document (`/.well-known/oauth-protected-resource`) names `resource: https://h/mcp`, not `https://h`, so a client that applies § 3.3 to the root URL must discard it; MCP lists the root form as valid discovery, and MCP clients compare `resource` with the server URL. Both forms are served; the path-inserted one is the strict one. `ProtectedResourceMetadata#paths`
- 🪶 `McpOperationHandler` is past 600 lines. Split session lookup, GET and DELETE away from POST dispatch and response writing. `McpOperationHandler`
- ⚠️ Task owner bindings are process-local (`TaskEngine#owners`). On another node that shares the connector (Temporal), or after a restart, an owned task reads as unowned and only the connector can refuse another caller. A shared store (the connector, or a task store SPI) would carry it; none exists. 2025-11-25 Tasks § Security says receivers MUST bind tasks to the authorization context, so this is a gap for multi-node and durable deployments. `TaskEngine#bind`
- ⚠️ A task without a `ttl` is bound to its owner only while its snapshot is cached: the binding ends with the snapshot (terminal + `keepAlive`, 5 min), and after that anyone with the id reaches it through the connector. `TaskEngine#evict`
- ⚠️ 2025-11-25 Tasks § Security Considerations: `tasks/list` **MUST** include only tasks associated with the requestor's authorization context. Tachyon hides tasks it knows are owned by another caller, but an unowned task (anonymous creator, server-published) is listed to every caller the connector lists it to, so an unscoped connector leaks it to authenticated callers. `TaskEngine#guard`
- 🪶 `tasks/list` hides foreign tasks after the connector built its page, so a page can be short, or empty with a valid cursor. Paging must move into the connector's own scoping, or the filter must refill the page. `TaskEngine#guard`
- 🪶 `TaskEngine.Binding#until` is `null` while the snapshot is cached and rewritten at eviction (`TaskEngine#evict`). Fixing it once at creation (`createdAt + ttl`, eviction only dropping a no-ttl binding) is shorter, but a no-ttl binding must stay live between `TaskEngine#bind` and the entry's `putIfAbsent`, and a later revision may change the `ttl` the binding was cut with. `TaskEngine#evict`
- ⚠️ A worker that publishes a task through `TachyonServer#tasks().publish` before the task tool returns creates an unowned entry, so the tool's later owned create is refused (`Internal error`). `InteractionContext#tasks()` (spec "new") would let it publish as the caller; not built. `TaskEngine#publishAs`
- ⚠️ No rate limiting on task ids: a caller can guess ids on `tasks/get` or name many ids in `subscriptions/listen` (one sequential connector `get` each). Owned ids answer `Task not found`, like unknown ones, so guessing learns nothing, but it costs connector calls. `TaskEngine#readableTaskIds`
- ⚠️ Authentication pauses reads only for a request whose body is still incomplete when a read ends, or once 64 KB is held (`AuthenticationHandler#HOLD_LIMIT`), so a request that arrives whole flips no `autoRead`. A large streamed body still pays two interest-set changes on epoll or kqueue, which `HttpRequestPathBenchmark` (an `EmbeddedChannel`, no selector) cannot show. Measure on a real socket before changing the limit. `AuthenticationHandler#hold`
- ⚠️ A refused caller that streams its body without `Expect: 100-continue` may see a connection reset instead of the `401`: the connection closes with unread body in the socket. A half-close that drains the rest would fix it. `AuthenticationHandler#respond`
- ⚠️ A token's audience matches the resource exactly after RFC 3986 §6.2.3 normalization, so `https://x/mcp/` is another resource than `https://x/mcp` and is refused, although an authorization server may echo whatever form the client sent. The MCP canonical-URI rule asks clients for the form without a trailing slash. Widen the match only if real tokens need it. `BearerTokenAuthenticationProvider#canonical`
- ⚠️ JMH A/B for fix #6 ran on a loaded machine (load average 3.9, a chat client at 122% CPU): every benchmark, including the paths the fix does not touch, fell 30 to 36% with identical B/op, so it shows no regression but is not a clean figure. Re-run `HttpRequestPathBenchmark` and `NettySseConnectionBenchmark` on a quiet machine before release. `HttpRequestPathBenchmark`
- ⚠️ A stream's timer is armed once, from the `Clock` that judged the token, and runs on the event loop's own time. A controllable test clock cannot advance it, and a wall-clock step after the stream started moves the real close away from `expiresAt`. `SseExpiry#arm`
- ⚠️ A stateless (2026) tool call whose streamed response is closed at the token's expiry loses its result: nothing can replay it, and `responseUndeliverable()` completes. The client repeats the call with a fresh token. A stateful (2025) client resumes to the result. `SseExpiry`
- 🪶 A rejection carries one `AuthenticationChallenge`, so a provider cannot offer two schemes at once, although `WWW-Authenticate` may list several (RFC 9110 §11.6.1). Add a list only when a use appears. `AuthenticationException#unauthorized`
- 🪶 A provider cut off at `authenticationTimeout` is not interrupted, so its virtual thread lives until it returns; `SecurityConfig#maxPendingAuthentications` caps how many such threads and held heads there can be. `AuthenticationHandler#expire`
- 🪶 The `scope` of every `401` is the whole configured baseline (`BearerConfig#scopesSupported`), not what the request needs. Least-privilege scope selection comes with the scope policy (fix #7b). `BearerTokenAuthenticationProvider#discovery`
- 🪶 `BearerConfig` refuses a resource with a query (RFC 8707 §2: SHOULD NOT include one), stricter than RFC 9728 §3, which allows a query in the resource identifier. Relax only if an MCP deployment needs it. `BearerConfig#requireResource`
- ⚠️ A `GET` to the metadata path with a body is answered at once; its body and trailing `LastHttpContent` flow on past `protected-resource-metadata` and the aggregator drops them. The next request on the connection is unaffected today; a handler added ahead of the aggregator must tolerate content that has no request. Verified: `AbstractDiscoveryTest#aGetThatCarriesABodyDoesNotDisturbTheNextRequest`. `ProtectedResourceMetadataHandler#channelRead`
- ⚠️ JMH A/B for fix #7a ran on a loaded machine (load average 6 to 13, a chat client at 120% CPU): across two pairs `authOff`, whose handlers did not change, moved −1.7% ops/s and +100 B/op (2455 → 2555), and `authOn` −5.0% and +1.6% ops/s, +112 to +168 B/op. The metadata handler allocates nothing on a request that is not for it (`instanceof` and `startsWith`), so the B/op shift is build-to-build variation, not attributed to it. The pair was measured before review round 1 moved the handler behind `cors` and gave `EndpointValidatorHandler` an `alsoServed` lookup on its mismatch path; that is not re-measured. Re-run `HttpRequestPathBenchmark` on a quiet machine before release. `ProtectedResourceMetadataHandler#channelRead`
- 🪶 Required scopes cover `tools/call` only: `resources/read`, `prompts/get` and the other methods have no declaration, and `tools/list` shows every tool to every caller, by decision. One mechanism would serve them (a descriptor attribute and the same exception), but no use has asked. `ToolMethodHandlers.ToolsCallHandler#handleAsync`
- 🪶 The Kotlin flat `tool(...)` / `registerTool(...)` overloads do not take `requiredScopes` (about a dozen signatures to thread it through); `toolDescriptor("x") { requiredScopes = … }` with the descriptor overload does. `ToolDescriptorScope#requiredScopes`
- 🪶 `McpDispatcher#dispatchRequestAsync` (the 6-argument overload) and `#dispatchNotification` (the 3-argument one) still dispatch as an anonymous caller, for direct invocation and tests. A transport that calls them forgets the caller silently; the two real transports call the overloads that take it. Delete the short overloads when the tests that use them move to the explicit ones. `McpDispatcher#dispatchRequestAsync`
- 🪶 Nothing but the Java `ServerBuilder#security` configures authentication: no Kotlin DSL (`security { }`), no Spring Boot property surface or bridge from Spring Security. `ServerBuilder#security`
- 🪶 A tool's required scopes are not checked against `BearerConfig#scopesSupported`, so a tool can require a scope the metadata does not list. Cheap to refuse at registration; left out because an empty `scopesSupported` is legal and the rule would need a second case. `DefaultToolRegistry#register`
- ⚠️ JMH for fix #7b (`ToolCallDispatchBenchmark`, check enabled against the check switched off in the same tree, three runs back to back) ran with load average 5.6 to 8 and a chat client at 120% CPU: `open` 90,217 ± 3,958 ops/s without the check, 89,238 ± 4,015 and 90,909 ± 2,331 with it; `guarded` 90,009 ± 2,031 without, 89,431 ± 1,631 and 89,557 ± 2,328 with.
